<b>Advisory:</b> misra-c2012-11.4
Justification: This deviation explicitly only concerns accessing memory mapped IO ports and registers with the macros in the device specific header files, which are provided in the device family pack (DFP) and included by <avr/io.h>, as this requires integer to pointer conversion. This deviation is essential for accessing IO ports on the device, but should be avoided in any other instances. This general approach has been thoroughly tested and is deemed to not cause any safety risk, unless there are bugs in the device specific header file in the device family pack. However, as each version of the library is thorughly tested for correct operation on supported devices for a specific version of the DFP, with the version listed in the release notes, the risk of such bugs causing a safety hazard is mitigated. Example:

//Write a value to IO port and TCB0 peripheral register
PORTA.DIR = 0xFF;
TCB0.CTRLA = TCB_ENABLE_bm;
//Where e.g. TCB0 on ATtiny3217 is defined as:
#define TCB0 (*(TCB_t *) 0x0A40)

<b>Required:</b> misra-c2012-20.9
Justification: False positive - this deviation explicitly only concerns the false positive on macros that are defined in the device specific header files which are provided in the device family pack (DFP) and included by <avr/io.h>. The tool mistakenly identifies that macros in the device specific header file are not defined before evaluation of the controlling expression of an #if or #elif directive containing such macros or macros which are defined using one or more device specific header file macros. The reason for the false positive is that the macro is not visible to the tool when performing the static analysis since <avr/io.h> uses the device specific macro (such as __AVR_AVR128DA48__), which is defined compile time, to determine which device specific header file to include. Example:

//INTERNAL_SRAM_SIZE is defined in the device specific headerfile
/* cppcheck-suppress misra-c2012-20.9 */
#if (DIAG_SRAM_DATA_REGION_LEN > INTERNAL_SRAM_SIZE)
#warning DIAG_SRAM_DATA_REGION_LEN cannot exceed the physical SRAM size.
#endif

<b>Required:</b> misra-c2012-2.2
Justification: Intentional - this deviation explicitly only concerns the usage of macro configurations resulting in unused code. The rationale for rule 14.3 states: "The presence of dead code may be indicative of an error in the program's logic. Since dead code may be removed by a compiler, its presence may cause confusion." This project uses configuration macros to determine if code should be included and if statements to test these configurations without recompiling. Using '#if' instead of 'if' would avoid the violation but mean that automated unit test would be harder to implement. If the config is set to DISABLED the code will be removed by the compiler.

<b>Advisory:</b> misra-c2012-10.5
Justification: Intentional - this deviation explicitly only concerns the typecasting of values stored in persistent GPR registers. The rationale for rule 10.5 states: "A cast to an essentially enum type may result in a value that does not lie within the set of enumeration constants for that type" This project uses persistent GPR registers to store 3 values over a reset. When read, these values are basically of uint8_t type. To keep consistency in user-facing code these values must be converted to the same type used before storing them to GPR. Since the same type is used before and after storing them it is deemed safe. The enums used are implemented with consecutive numbering so that only values above the largest defined member is invalid when converting. In addition to using the same type in storing and retrieving, the project uses validation of the stored number to ensure that it is within the defined members of the enum.

<b>Advisory:</b> misra-c2012-15.5
Justification: Intentional - multiple returns should only be utilized as early exits in guard clauses where a condition determines that no further code should be executed for that function. Guard clauses enhance code readability by minimizing the use of if/else statements. Employing early returns for other application flows is not permitted as part of this deviation justification. The rationale for rule 15.5 states: "A single point of exit is required by IEC 61508 and ISO 26262 as part of the requirements for a modular approach. Early returns may lead to the unintentional omission of function termination code. If a function has exit points interspersed with statements that produce persistent side effects, it is not easy to determine which side effects will occur when the function is executed." This project uses early returns in situations where a state or value determines that the rest of the code shall be skipped. Using early returns instead of if/else in these situations makes it more explicit and separates the test from the rest of the code.

<b>Advisory:</b> misra-c2012-2.5
Justification: Intentional - this deviation explicitly concerns macros defined in the tasks_config.h file that may become unused depending on the selected configuration or usage of optional Task Managers and Tasks. Depending on the Application requirements, certain macros will intentionally remain unused. Allowing unused macros enhances flexibility, maintainability, and ease of configuration without requiring modification of the framework source code itself. Since the presence of unused macros does not introduce functional behavior or affect compiled binaries, it poses no safety risk. The Application implementation has the option to manually remove unused macros if desired, which further mitigates any potential confusion.
